## 1. 背景与目标

当前「专家后台」（`apps/admin`，本地 :4174/admin/）是开发阶段的技术界面：手动粘贴双 Token 才能连接、与官网同源部署、非标准管理系统形态。

**目标**：改造成与官网完全分离的独立管理系统——

1. 官网与后台在**页面、路由、构建产物、部署入口、权限**上彻底独立，普通用户/投资人永远看不到后台。
2. 后台使用**账号密码登录**，移除手动输入 Token 的界面。
3. **不要审核流程**：管理员直接编辑、直接发布，一步到位。不再有「提交审核 → 另一人发布」的双角色链路。
4. 采用 Ant Design 管理系统范式：左侧导航、数据表格、状态筛选、抽屉编辑、版本历史。

**保留的核心机制**（不属于审核流程，不可删）：

- **发布版本不可变**：每次发布生成带内容哈希的版本快照，旧版本可查不可改。报告的 citations 和全链路溯源依赖它，是产品的核心卖点。
- **操作留痕**：谁在什么时间发布/修改了什么，记录 actor 与时间（自动记录，无需第二人确认）。

**非目标**（本期不做）：

- 审核流、双角色分离、reviewer 令牌体系（全部移除）；
- 逐条报告查看/坏例标注、命盘档案管理页（二期 B 再议；一期仪表盘只做**只读聚合指标**，见 §2.7）；
- 官网视觉与业务流程改动（仅移除后台入口链接）；
- 多租户、完整 RBAC。

## 2. 功能范围（第一期）

### 2.1 专家资料管理（主体模块）

- 资料类型：`article`（文章/知识正文）、`rule`（结构化空间规则）——`ExpertAssetKind` 定义在 `packages/knowledge-contracts/src/index.ts:57`。
- 功能：
  - 列表页：表格（标题/类型/状态/当前版本/更新人/更新时间），按类型和状态筛选，分页，**标题关键词搜索**；
  - 创建/编辑：抽屉或整页表单，支持 TXT / Markdown / JSON 导入（PDF/DOCX 仍留待后续文档抽取服务）；
  - 发布：一键发布 → 直接生成新的不可变版本（内容哈希 + actor + 时间）；二次确认弹窗展示版本号与哈希摘要；
  - 归档：下线资料，不再进入报告检索；
  - **删除（物理删除）**：草稿可直接删除；已发布资料删除需输入标题确认的强提示弹窗；若该资料的任一发布版本被现有报告 citations 引用，服务端返回 409 拒绝删除并列出引用它的报告数（溯源不可断，此类资料只能归档）；删除动作写操作留痕（谁、何时、删了什么）；
  - 版本历史：查看历次发布版本、版本间 diff；
  - 修订并发控制保持现状：`expectedRevision` 乐观锁（文件模式写队列，PostgreSQL 行锁）。

### 2.2 Skill 管理（一等模块）

现状：Skill 是专家资产的一个类型（`kind: 'skill'`），随知识资料一起存储和发布；报告生成时 Harness 实际加载的 Skill 在 `.agents/skills/fengshui-report`（由 `harness.fengshui.patch.yml` 挂载，配合 `fengshui-report-plugin/`）。

第一期功能：

- 后台独立的「Skill」导航项，管理 `kind: 'skill'` 的专家资产：列表、编辑（Skill 正文/指令内容）、发布版本、归档，交互与资料管理一致；
- Skill 详情页展示**当前报告链路实际生效的 Skill 信息**（名称、来源、哈希——从服务端读取 `.agents/skills` 与插件的实际状态，只读展示），让管理员知道"后台里发布的 Skill 资产"与"Harness 实际加载的 Skill"的对应关系；
- 边界：第一期**不做**「后台发布 Skill → 自动替换 Harness 运行时 Skill 文件」的热更新链路。若需要该能力，作为二期单独设计（涉及运行中报告的一致性，需要停机或版本化加载策略）。文档中必须向接手人明确这一点，避免误解为后台可以直接改 Harness 行为。

### 2.3 规则配置（八字流派规则）

- 现状：`schemaVersion: 2` 数据型决策表（时间默认参数、旺衰/格局/神煞规则条目），路由 `/v1/bazi-rule-profiles*`。
- 功能：
  - 规则配置列表 + 状态筛选（草稿/已发布/已归档）；
  - 规则编辑：保持现有约束——只能引用固定事实路径、固定操作符、已发布知识版本，**不可执行脚本**；
  - 一键发布 → 不可变版本（内容哈希 + actor + 时间）；
  - 版本历史与规则条目 diff；
  - 命盘与规则版本的绑定关系只读展示（哪些命盘版本绑定了该规则版本）。

### 2.4 问真对照（迁移，不扩展）

- 现有采集/校验/证据上传功能原样迁入新框架（行政区选择器、`POST /api/v1/bazi/compare`、SHA-256 证据、fixture 列表）；
- **移除其中 reviewer 令牌依赖**：「接受差异」动作改为任一管理员可操作（保留逐条分类 + 理由的表单约束，`bug` 仍不允许接受——这是数据质量约束，不是审核流程）；
- 不新增功能。

### 2.5 登录账号（固定单一 admin）

- **不做账号管理模块**。第一期固定一个 admin 账号：用户名/密码来自服务端环境变量（如 `ADMIN_USERNAME` / `ADMIN_PASSWORD`，密码在环境变量中存哈希或首次启动时哈希落库）；
- 后台只有登录页，没有注册、账号列表、角色分配等任何界面；
- 改密码 = 改环境变量重启，Demo 阶段可接受；多账号体系留待二期。

### 2.6 工作台仪表盘（首页，C 端运营监控大盘）

登录后第一屏。定位：**监控 C 端产品运行状态**，内容统计为辅。全部为只读聚合指标，数据来自现有 stores（报告、命盘、媒体、知识、问真），不需要新增采集。

布局（自上而下）：

1. **C 端核心指标卡（一排）**：
   - 报告：今日/累计生成数、成功率、平均生成耗时（来自报告记录状态与 `generationProvenance` 时间戳）；
   - 失败中：当前 queued/failed 任务数（failed > 0 时卡片红色告警）；
   - 命盘：累计命盘档案数、今日新增命盘版本数；
   - 媒体：当前待清理上传数、24h 清理任务状态。
2. **图表区**：
   - 近 30 天报告生成趋势（按天，成功/失败分色堆叠）；
   - 报告失败原因分布（校验失败/知识检索失败/模型超时/vision 失败等，来自报告记录失败状态字段）；
   - 排盘坐标覆盖率进度条（2614/3311，现成审核数据）。
3. **内容运营区（次要，小卡片）**：资料/Skill/规则总数与已发布数、问真样例数与最近 `wenzhen:diff` 通过状态、最近发布记录列表（actor、时间、版本）。
4. **系统健康条**：存储驱动（file/postgres）、API /ready 状态、DeepSeek key 是否配置（只显示有/无，不显示值）。

实现约束：

- 新增聚合接口 `GET /v1/admin/dashboard`，服务端一次算全，前端不打散接口；
- 指标可 60s 轮询或手动刷新，不做 WebSocket 实时推送；
- 图表库：`@ant-design/charts`（与 antd 一致性好）；
- **边界**：卡片/图表只到聚合数字层；点击不跳转到单条报告详情（那是二期 B），失败任务卡只显示计数与最近失败时间。

### 2.7 官网侧改动

- 移除 `apps/web` 中一切指向后台的入口链接；
- 官网构建产物 grep 不到后台地址（构建期就不存在，不是 CSS 隐藏）。

## 3. 登录与会话方案

- 账号密码登录，服务端签发 HttpOnly + SameSite Cookie（独立 cookie 名，与官网匿名凭证 `fengshui_principal` 无关）；
- 密码哈希：argon2id 或 scrypt；账号表进 PostgreSQL（新迁移文件放 `apps/api/migrations/`）；
- 登录失败简单限流（计数 + 冷却，Demo 阶段不做验证码）；
- **过渡期兼容**：现有 `ADMIN_API_TOKEN` 环境变量保留为应急/服务间通道（curl 可用），但后台 UI 不再出现 Token 输入框；
- **移除**：`ADMIN_REVIEWER_API_TOKEN`、`requireExpertReviewer`（`apps/api/src/app.ts:172-177`）及所有「提交人 ≠ 审核人」校验。原 reviewer-only 路由（知识/规则发布、问真差异接受）改为普通 admin 权限。

## 4. API 改造点（apps/api）

新增（前缀 `/v1/admin/`）：

1. `POST /v1/admin/sessions`（登录，校验固定 admin 账号）、`DELETE /v1/admin/sessions`（登出）、`GET /v1/admin/sessions/me`。不做任何用户管理端点。

改造：

2. `requireAdmin`（`app.ts:167`）扩展为「管理员会话 或 应急 Bearer Token」双凭证；actor 固定为 `admin`（历史记录里的旧 actor 字符串保持可读，标注 legacy）；
3. 发布类路由（knowledge publish、rule profile publish、wenzhen accepted-difference）从 reviewer 权限降级为 admin 权限；
4. 发布版本的 provenance 记录简化：编辑 actor + 发布 actor 可为同一人，字段保留（兼容既有数据结构和报告 citations）。

不改动：

- 官网匿名主体体系、报告生成、Harness、vision、知识预取链路（`KNOWLEDGE_MCP_TOKEN` 内部通道原样保留）；
- 已发布版本不可变语义、`expectedRevision` 并发控制；
- 问真 fixture/evidence 文件存储路径（`.data/evidence/wenzhen/`）。

## 5. 部署方案（独立后台）

```
nginx-portal (:8080)         → 官网静态 + /api 反代     （投资人可见）
nginx-admin  (独立端口/域名)  → 后台静态 + /api 反代     （仅内部）
api (:3001 内网)             → Fastify，两边共用，权限在应用层区分
```

- `compose.yaml` 已拆出独立 `admin` service（新 nginx 容器）；当前后台仍以 `/admin/` base path 提供静态资源，默认端口为 `ADMIN_PORT=8081`；
- 后台端口不对公网映射（或加 IP 白名单/反代 Basic Auth 前置）；
- 后台地址不出现在官网产物、README 用户可见部分、API 错误信息中；
- 同步更新 `docs/deployment.md`。

## 6. 视觉与交互

- Ant Design 默认视觉（白底、信息密度优先），不定制品牌主题；
- 布局：登录页 → 左侧导航（工作台/专家资料/Skill/八字规则/问真对照）+ 顶部用户区（显示 admin、登出）+ 内容区；

- 资产详情页展示操作留痕时间线（actor、时间、动作、版本号）。

## 7. 验收标准

1. 官网构建产物 grep 不到任何后台入口/地址；
2. 未登录访问后台任意路由 → 登录页；用环境变量里的固定 admin 账号可登录，错误密码被拒且有限流；
3. admin 登录后：创建资料 → 编辑 → 一键发布，生成不可变版本（哈希 + actor + 时间齐全）；旧版本可查不可改；
4. Skill 模块独立可见，管理 `kind: 'skill'` 资产，详情页能看到 Harness 实际生效 Skill 的只读信息；
5. 规则配置发布后，新命盘可绑定新版本；历史命盘绑定的旧版本不被改写；
6. 问真对照全流程可走通且 `pnpm wenzhen:diff` 通过；「接受差异」不再需要第二枚令牌；
7. Token 输入框从 UI 消失；`ADMIN_API_TOKEN` 应急通道 curl 验证仍可用；`ADMIN_REVIEWER_API_TOKEN` 相关代码已删除；
8. `pnpm test`、`pnpm typecheck`、`pnpm build`、`pnpm test:postgres` 全绿；新增登录会话/发布的单元与 PostgreSQL 集成测试；
9. Compose 起后后台在独立 service/端口，官网端口访问不到后台静态资源。

## 8. 风险与注意事项

- **仓库当前零提交**（分支 `feature/chart-persistence` 全部 untracked）：动手前必须先建立初始 commit；
- `apps/admin/src/main.tsx` 约 1900 行单文件：建议引入 antd + react-router 后按页面拆分重写，不要在单文件上继续堆；
- 移除审核流会触碰大量现有代码与文档：README、`docs/knowledge-architecture.md`、API 测试里都有「提交人≠审核人」「reviewer 令牌」的表述和断言，需要一并清理，避免文档与实现矛盾；
- 现有 PostgreSQL 发布审计结构（提交/审核/发布三方 actor 字段）不要删列，改为允许同一 actor，保持旧数据可读；
- 本地文件存储模式（`STORAGE_DRIVER=file`）：账号/会话功能要求 PostgreSQL；文件模式仅保留环境变量 Token 应急登录（开发用途），与「生产强制 postgres」既有约束一致；
- Skill 后台管理与 Harness 运行时 Skill 是两条线（见 §2.2 边界），接手人不要自行打通热更新。

## 9. 建议实施顺序

1. 初始 commit + 切 `feature/admin-console` 分支；
2. API：固定 admin 会话登录 + `requireAdmin` 双凭证改造 + 移除 reviewer 体系（含测试与文档同步）；
3. 后台骨架：antd + react-router（登录页、布局、路由守卫）；
4. 逐模块迁移：专家资料 → Skill → 八字规则 → 问真对照（API 契约不变，只换 UI 与权限入口）；
5. 官网移除后台入口；
6. compose 拆分独立 admin service + 更新 `docs/deployment.md`；
7. 按 §7 验收，全量跑验证命令。

## 10. 开放问题（继续对齐中）

### 10.1 后台辅助「训练 agent」（2026-09-02 已确认分期：一期 A，二期 B）

产品负责人的诉求：后台不只是管内容，还要能持续改进报告 agent 的输出质量。

**已确认决策**：一期只做 A（知识/规则/Skill 管理，即本文档 §2 全部内容）；**B（报告查看与坏例标注）列入二期**；C/D/E 暂缓、不排期。

技术事实（边界先说清）：

- 本系统**不微调模型**。DeepSeek 模型本身不可训练，报告质量的全部可控手段是：注入 prompt 的已发布知识/规则、Skill 指令、以及生成后的校验器。因此"训练 agent"在本项目里的真实含义 = **专家通过后台治理模型可见的全部内容，并用反馈闭环持续迭代**。
- 现有机制已经是一半：已发布知识由 API 预取注入 prompt（citations 固化）、规则派生结论写入 provenance、模型只能引用不能补写。

候选功能全景（留档备查）：

## 11. 附：已发布内容如何被报告 agent 使用（供实施时理解链路）

后台管理三类内容，它们进入报告 agent 的方式各不相同，**都不是模型自己检索**：

1. **专家资料（article/rule 知识）**：报告生成前，API 用服务端内部令牌（`KNOWLEDGE_MCP_TOKEN`）调用知识接口检索**已发布**资料，筛选相关条目后截断（预算：最多 8 条 citations、每条摘要 ≤300 Unicode 字符），**固化写入 prompt 和报告记录的 citations 字段**。检索实现是**关键词计分**（`apps/api/src/knowledge.ts:226-236`：查询分词后在 标题+tags+正文 里数命中次数，按分排序取 top-N），**不是向量 RAG、没有 embedding**——这是刻意保持的确定性设计；语义检索升级（向量库/混合检索）属于未来可选项，一期不做。模型没有任何检索工具（无 MCP/文件/网页），只能看到被注入的内容。缺内部令牌时检索 fail-closed，报告落为 failed 而非裸 500。
2. **八字流派规则（rule profile）**：由程序确定性评估（`apps/api/src/rules.ts` 的 `evaluatePublishedRules`），命中结论写入 provenance。模型**只能逐字引用**已派生结论，不允许自己补写旺衰/格局/神煞判断；冲突或未命中的规则显示为待审核。
3. **Skill**：模型侧唯一可见工具是 `skill`，加载 `fengshui-report` Skill 指令（`.agents/skills/fengshui-report` + `fengshui-report-plugin/`），约束报告结构、必含章节与文化娱乐提示语。
4. **出口校验**：生成结果经 `apps/api/src/report-validator.ts` fail-closed 校验——每条知识引用必须带标题/版本号/来源标签，每条规则命中必须带原样结论文字，缺失即整单失败，不向用户返回未审查正文。

因此后台「编辑→发布」的实际效果：**下一次报告生成立即使用新版本内容，且报告可溯源到确切版本哈希**。这就是"训练 agent"的一期机制。
