# 居境 Compass 长期开发方案

## 产品定位

投资人 Demo 先证明一条完整闭环：用户录入出生资料与住宅资料，系统用确定性程序排出命盘，上传并标注多张住宅照片，后端执行视觉观察、风水规则与专家知识检索，最后由 DeepSeek Harness 生成一次性报告。系统不是持续聊天产品，模型不负责排盘、不发布知识、不改规则。

## 竞品参考结论

问真八字网页排盘的关键交互包括：公历/农历/四柱切换、出生时间选择器、出生地址选择、夏令时、真太阳时、早晚子时等显式参数。测测 App 的生辰页突出四柱表格、十神、藏干、支神、纳音、空亡、地势、神煞、合盘与流盘入口。我们的命盘页应覆盖这些“专业字段与参数显式化”能力，并额外强调版本化、差异报告、专家知识依据和住宅图片证据链。

## 阶段 0：当前 Demo 收口（1–2 周）

目标：让投资人看到完整闭环，不追求最终 UI 质感。

必须验收：

- 出生日期/时间点击后唤起应用内选择器，支持公历、农历、四柱入口。
- 省、市、区县地点选择器替代经纬度手填；经纬度、时区由地点库自动带出。
- 真太阳时、夏令时、早晚子时、起运算法成为可见参数，并随命盘版本保存。
- 命盘页是独立页面，可从导航随时进入，展示四柱专业表格。
- 大运、流年、流月、流日、流时有明确数据区，未实现字段不能由模型补写。
- 住宅多图上传、每图空间/镜头朝向/备注标注可用。
- 报告状态链路可见：上传、创建任务、模型分析、校验、完成。
- 专家后台支持资料上传、标签、审核发布；API 只读取已发布版本并固化到报告任务证据中。
- Harness 报告生成演示走 SDK Profile；模型侧只开放 `fengshui-report` Skill，并只读取 API 预取后的结构化证据、规则命中和知识引用。

当前收口状态（2026-09-04）：上述主链路均已进入可运行 Demo；日期选择器已由服务端农历月表约束，2023 年可区分二月与闰二月。问真对照已具备后台预览、证据上传、证据确认、并发安全追加保存、PostgreSQL 生产落库和逐条接受流派差异的机制；当前已有 6 条真实问真截图哈希样例进入自动化差异报告并通过，覆盖普通专业表格、立春边界、23 点子初换日、乌鲁木齐 `dstPolicy: ignore`/西部经度、农历闰四月，以及公开可见的动态流盘。离线报告会同时检查脱敏 `evidence-manifest.json` 和私有截图本体的存在性、大小、SHA-256、MIME 文件签名；截图本体保存在本地私有证据目录，不进入仓库。31 条采集矩阵固定为 6 条 `verified` 与 25 条 `pending-capture`，后者不包含推测输出或伪造证据，必须在真实采集后逐条转为核验样例。6/6 样例的四柱及已断言字段通过，但真太阳时仍有问真显示分钟与当前 v2 近似算法相差 1 分钟的样例，当前未用硬编码追平。默认和历史缺失版本仍回放 v2；用户请求或已发布规则档案可显式 opt-in 到 fractional-year NOAA v3，并把实际版本写入命盘、报告和问真差异。四柱表已输出可复算的基础神煞；旺衰、格局和完整流派神煞已经具备专家审核 `schemaVersion: 2` 数据型规则执行机制，剩余风险是录入真实专家规则内容、完成更多双人审核样例，并扩展流年神煞与精确起运字段对照。Stage 1 对照目标仍为至少 30 条真实样例，不能把 31 条规划矩阵宣传为已全部验证。

住宅数据层收口状态（2026-09-03）：住宅已从报告内一次性文本升级为主体隔离的多档案模型，文件存储与 PostgreSQL 都采用 `ResidenceProfile -> ResidenceVersion` 追加版本结构，支持乐观锁、软删除、恢复和历史版本读取。报告同时固定 `chartVersionId` 与 `residenceVersionId`，后续修改任一档案都不改写历史报告。户型几何可通过 `floorplan-nine-grid-v1` 确定性生成 `kitchen.south` 与 `bathroom.near-center` 两类受控事实，并以 `program-nine-grid` 来源在规则执行前进入证据链；穿堂动线仍因缺少门窗线段几何而禁止推断。公开报告接口会同步拒绝未确认上北、越界房间、过大几何输入和匿名人工 override。当前报告列表已支持按成员、住宅和回收站组合筛选，Admin 用户详情可查看用户的成员命盘、住宅档案和两类维度下的报告计数。PostgreSQL 真实门禁已覆盖账号、问真、知识、命盘、住宅、报告和八字规则档案的集成测试；仍不能据此宣称已完成阶段 1 的 30 条问真真实样例目标。

问真差异通过口径按实际断言字段计算，不代表整页一致。当前 6 条真实样例已覆盖四柱、时间校正、专业表、大运，以及公开可见的流年与流月；流日、流时仍为 0，完整动态五层场景 `wz-048` 继续 pending。未采集的字段不会因同属一类而被计为已覆盖。manifest 同时保留专业表、大运和四类动态流盘的字段计数及逐样例叶子路径；旧的五类 `coverage` 汇总继续兼容。`GET /v1/bazi/wenzhen/diff`、用户端命盘页和专家后台都展示同一份覆盖状态。每条新接受差异必须选择依赖、流派规则、时区/地点或显示/舍入分类并填写理由；产品缺陷不得接受，旧无分类记录保持可读。

## 阶段 1：排盘基础产品（1–2 个月）

目标：稳定、可复算、可对照。

排盘引擎：

- 完整农历/公历互转，保存源输入和归一化公历/农历。
- 节气边界测试覆盖节前、节后，后续补充精确边界样例。
- 子初换日配置落库，并能证明日柱差异。
- 历史时区和夏令时按 IANA 时区处理，保留实际偏移、标准偏移和 DST 分钟。
- 城市地理数据库从 Demo 子集扩到全国行政区县，并支持版本号。行政树以六位代码为事实源，坐标主源采用带 CC BY 4.0 署名的 GeoNames 中国快照；原始 GeoNames 层级码必须先经保守 crosswalk 和冲突审核，不能按同名地区猜测。
- 起运算法按流派配置，保存所用 profile。
- 与问真样例建立差异报告：同输入、同参数、比对四柱、校正时间、大运起运。

命盘产品：

- 专业命盘表补齐支神、基础神煞、旺衰、格局等可执行字段；完整流派神煞和格局判断通过固定事实路径、固定操作符和已发布知识版本引用执行，未发布、未命中或冲突时显示待审核。
- 命盘导出 PDF/图片基于已保存快照生成，不触发重新排盘。
- 命盘历史版本可查询、回看；更新采用乐观锁。
- 删除采用软删除；同匿名主体可恢复，报告引用的历史版本不受影响。

## 阶段 2：住宅风水报告产品（1–2 个月）

目标：从“能生成”变成“有依据、能复核”。

- 图片视觉识别拆成空间事实，不直接产生命理建议。
- 住宅档案补充朝向、楼层、户型、入户门、厨房、卧室、卫生间、采光等结构化字段。
- 风水规则库以条件、事实路径、优先级、结论文本发布，不接受纯自由文本规则。
- 专家知识库按资料、案例、禁忌、调整建议分类型管理。
- 报告必须展示：输入摘要、命盘摘要、空间观察、规则命中、知识引用、建议边界。
- 报告失败关闭：缺少视觉同意、无照片、Harness 不可用、知识检索失败时给明确状态。

## 阶段 3：生产化（2–3 个月）

- 用户系统与匿名档案认领。
- PostgreSQL 正式迁移、对象存储、加密配置、数据保留期。
- 后台权限：资料上传、审核、发布、回滚分离。
- 可观测性：报告任务耗时、模型失败率、规则命中率、知识引用覆盖率。
- Eval：问真差异样例、视觉事实样例、报告引用完整性、权限失败路径。
- 导出：正式 PDF 模板、长报告分页、图片分享图。

## 当前工程边界

- 前端：`apps/web`，投资人端报告和独立命盘页。
- 后端：`apps/api`，报告任务、命盘档案、媒体、知识、Harness 调用。
- 管理后台：`apps/admin`，专家知识草稿、发布和回滚。
- 排盘引擎：`packages/bazi-engine`，所有八字计算必须在这里完成。
- 地点库：`packages/geo-data`，出生地点到经纬度/时区映射。
- 共享模型：`packages/domain`，API、前端、引擎共同使用的数据契约。
- Harness 插件：`fengshui-report-plugin`，只负责编排 API 提供的结构化输入生成报告。
- 知识检索：`services/knowledge-mcp` 保留为内部只读服务边界；报告生成前由 API 预取并固化引用，不直接暴露给模型侧 Harness 工具。

## 验收原则

每个能力必须同时有三类证据：界面入口、后端或引擎契约、自动化测试。无法自动化的外部竞品对齐，先沉淀成样例和差异报告，不口头宣称完全一致。
